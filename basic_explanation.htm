What one update does to the spine

One record, one field write, one commit. This traces it structure by structure — what gets cloned, what stays a shared pointer, and why the object's Id comes out the other side completely unchanged even though its value did not.

Starting point

A model with one record

The model has exactly one chunk allocated — slot 42 falls inside chunk 0 (kChunkSize = 4096 slots), so that's the only chunk that exists at all. It holds one live slot; the other 4095 are empty. Model::spine_ (the writer's working copy) and the published Root's spine point at the literal same Chunk object — nothing has diverged yet, so there is nothing to copy.

shared_ptr, untouched by any commit in flight
Step 1

Begin a transaction, call update()

Model::begin() takes a Snapshot of the current Root (v1) as the transaction's base — a pointer copy, no lock. txn.update<Account>(id) then hands back a mutable pointer to a fresh clone of that object. The clone lives entirely outside the spine: not linked into any Chunk, not visible to any Snapshot, not touched by commit_mu_ at all. Its Id is copied verbatim from the original — {42, 1} — because it names the same object; only its field values are free to change, and can change any number of times, in any order, before commit.

Step 2 · inside try_commit(), under commit_mu_

Apply: clone the chunk, not the model

Once try_commit() takes commit_mu_ and confirms nothing else touched id 42 since this transaction's base, apply_update() installs the clone. The old object is retired — marked invisible starting at the next version, not freed — and set_slot(42, new_ptr, gen=1) writes the new pointer in. That call starts with cow(chunk 0): first touch of a chunk in this attempt clones the whole chunk, all 4096 slots, in one memcpy. Model::spine_[0] is repointed at that clone; the original Chunk 0 is left completely alone — still exactly what Root v1 points at.

original chunk — still what Root v1 sees cloned chunk — spine_[0]'s new target
Step 3

Publish: a new Root, mostly borrowed

publish_now() bumps version_ to 2 and builds a fresh Root. r->spine = spine_ copies the vector — one shared_ptr handle per chunk, O(total chunks), never O(objects). For this model, that's a single pointer: slot 0 now names Chunk 0'. Model::root_ is swapped to r atomically; every Snapshot taken from this point on sees version 2. Root v1 is not modified, not decremented, not touched — it simply keeps existing, held alive by whatever still references version 1: a live Snapshot, or another transaction's still-open base().

Generation only moves on slot reuse, never on an update. If this record were removed instead, and something later allocated slot 42 for a new object, alloc_slot() would read the slot's current generation (1) and mint {42, 2}. A stale Id{42, 1} held by an old reference would then fail slot_lookup's generation check forever, rather than silently resolving to the new occupant — that's invariant 5, and it's the entire reason Id carries a generation at all instead of just an index.

The other half of Root

Index maps are a trie, not a chunk array

Root holds more than the spine. by_type, by_key, by_cached_field, and every other index in the struct are each their own copy-on-write structure — but a different shape from the spine's flat array of chunks. They're a hash array-mapped trie (pmap::TrieCore): a persistent, 32-way branching tree, addressed by hash bits instead of a slot number.

A Node carries one 32-bit bitmap — one bit per possible child at this level — and an array sized to exactly popcount(bitmap), positionally compacted. There is no slot for a child that doesn't exist: unlike a Chunk, which always allocates room for all 4096 slots whether they're full or not, a trie Node with 3 real children allocates for 3. Each level consumes 5 bits of a 64-bit hash, so descending one level means shifting 5 bits further in; a child slot holds either another Node (keep descending) or a Leaf (the actual entry). Two keys whose hashes agree on the slices consumed so far are pushed one level deeper, into a new child Node, until their hash bits differ. Only when the hash bits run out — two keys with the identical 64-bit hash — do they share a Leaf through a collision chain.

Step 2, continued · reconcile_all_indexes()

A field update walks the trie too

Say Account also declares status via define_fields(), and this same commit changes it alongside the balance: "active" → "past_due". Right after apply_update() installs the fully-written clone into the spine, reconcile_all_indexes() runs — and for a cached field, that means bucket_erase against the old value's bucket, then bucket_insert against the new one, both on Root::by_cached_field["status"].

  • Erase: id 42 comes out of the "active" bucket's own inner trie (a PersistentSet<Id>). Id 27 is still in there, so the bucket survives with one member; had 42 been the last one, bucket_erase's contract drops the whole "active" entry from the outer trie rather than leaving an empty tombstone.
  • Insert: id 42 goes into the "past_due" bucket. No such bucket existed, so one is created — seeded from Model::node_pool_, the same pooled allocator every other trie node in this commit draws from, not a bare heap allocation.

Each of those two calls does to the outer trie exactly what cow() did to the spine: walk root-to-leaf along the touched key's path, cloning every Node it passes (clone_node + RcHandle::adopt), and returning the original handle, untouched, for every sibling it never visits. The "trial" bucket sits on neither path this commit takes, so it is the identical RcHandle — not a copy of it — in both the old index and the new one.

Beyond Root · writer-private state

The referrers index is a flat table, not a trie

Everything so far — the spine, the index tries — is published state: immutable, structurally shared, cloned along the write's path. Model::referrers_ is the one structure that is neither. It is the reverse index, “who points at this target?”, that the cascade delete in remove_raw() walks, and it is only ever touched by the thread holding commit_mu_ (invariant 7). No reader can see it; the published counterpart for readers is by_cached_reference. Nothing shares it between versions, so it can be mutated in place, and a table that mutates in place is exactly what a trie's path-copying would only slow down.

It is split by referring field (Order::account, Order::account_scan, and so on). Each field has its own index from a target's slot index to the ids of the objects whose field points at that slot. The key is the bare slot, not a full Id, because only a slot's live generation can ever be the target of a live ref. Because the field is the outer key, an edge is stored as just the referrer's Id, 8 bytes; the field, and whether it is nullable, are stored once per field instead of on every edge.

Inside one field's index, a target's referrers have two storage forms, chosen by how many there are.

the index itself small form — a vector of ids, scanned linearly hub form — a flat hash set of ids

Why two forms

A vector is the smallest and fastest thing for a handful of ids. But removing one means finding it, and finding it in a vector is a scan: for a hub, every order that is deleted or re-pointed costs the whole referrer count. In hub form the same removal is one hash lookup. The two forms swap at fixed thresholds, counted per target and per field, and the gap between them is deliberate: a target hovering near a single threshold would otherwise convert on every add and remove, and each conversion costs time proportional to its size. The form is chosen per target, not per field, because one field can hold both many small groups and a few very large ones, and its cardinality is not known in advance.

small form hub form either form, whichever it already has

Inside a hub: FlatSet

In hub form, a target's referrers through one field are a fset::FlatSet<Id>: open addressing with linear probing, one contiguous array of cells and no allocation per key. A key's home cell is where its scrambled hash points; a lookup starts there and steps forward, wrapping at the end, until it finds the key or reaches an empty cell. That walk is the probe run. The table is a power of two in size and never more than three-quarters full, so every run ends at an empty cell, and Id{} (the null id) is what marks a cell empty.

Deletion is the interesting part. Simply blanking a cell would cut a probe run in two and hide the keys behind the hole, and a marker for “deleted” would make runs grow longer forever. Instead erase() does a backward shift: it scans forward from the hole and pulls back any key whose home cell is not past the hole, stopping at the first empty cell. No tombstone is ever left behind.

the key erased, and the cell it leaves empty the key that moved keys that did not move

What splitting by field buys

Measured on this repository, with 200,000 Orders spread over a varying number of Accounts. Memory is resident growth per order. The old layout kept one vector of 24-byte RefEdge per target, so the per-field layout gains more the more referrers each target has, and costs nothing measurable when every target has one.

Removing every order of one hub in a single commit, in random order, took 6.1 s (100,000 orders) and 20 to 32 s (200,000) with a vector per target, and takes 2.5 s and 5.8 s with hub form. The per-removal cost stays near 25 to 30 microseconds instead of growing with the hub. Removing the hub target itself did not change: the cascade takes the hub's whole entry out in one step, so its referrers' own removals find nothing to search.
